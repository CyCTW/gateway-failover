# Gateway Failover 設計規格（初版實作依據）

> 用途：交給 Claude Code 作為實作初版的依據。內容整理自設計討論，尚未決定的事項列在最後一節，實作前請先向我確認。

## 1. 目標與範圍

實作交易系統 gateway 的 failover 機制初版。Gateway 負責與券商/交易所連線，轉送策略委託並管理回報。

初版要涵蓋：
- 先寫後送的本地日誌（WAL）與重啟後的狀態重建
- 斷線自動重連與恢復交易的決策
- 券商回補與對帳
- 緊急全撤單流程
- 獨立 kill switch 程式
- 模擬券商與 failover 情境測試

初版不做：真實券商 API 串接、自動平倉、跨機複寫（保留介面即可）。

## 2. 核心原則

1. **真相分兩邊**：委託狀態與成交以券商為準；策略歸屬、母單等本地資訊以自己的日誌為準。
2. **只存事實，不存推導結果**：訂單簿、部位、風控額度一律由日誌重算。
3. **一套狀態機，三種輸入**：即時回報、本地日誌重播、券商回補走同一套狀態更新程式碼。
4. **處理與順序無關**：回報套用必須冪等且可交換。
5. **不確定時假設最壞情況**：未知狀態的單視為可能還在、也可能已成交，風控額度先佔用。
6. **無法自動判定就停止交易**，交給人工，不讓程式猜測。
7. **恢復期間不接新單**，對帳通過才開放。

## 3. 前提假設

- 券商回補 API **不能指定序號，只能從頭回補**當日全部回報。
- 回補的回報順序可能與當初即時收到的順序不同，中間狀態可能被合併或省略。
- 券商另有「未成交委託查詢」與「部位查詢」API，通常比完整回補快。
- 撤單通常需要委託書號；送出後未收到確認的單沒有委託書號。
- 同帳號多策略共用，策略代號不會傳到券商，除非編進 ClOrdID 或自訂欄位。

## 4. 元件

| 元件 | 職責 |
|---|---|
| Gateway | 連線、送單、收回報、WAL、狀態機、對帳、推送給策略 |
| Order State Machine | 套用請求與回報，維護訂單簿、成交集合、部位 |
| WAL | 只追加的事件日誌 |
| Reconciler | 以回補資料建影子簿，與本地比對，產生差異清單 |
| Connection Manager | 重連、抖動偵測、恢復模式決策 |
| Kill Switch | 獨立 process，無狀態，向券商查詢後全撤 |
| Watchdog | 監看 gateway 心跳，觸發重啟或 kill switch |
| Mock Broker | 測試用，可注入各種失敗 |

## 5. ClOrdID 與策略歸屬

- ClOrdID 編入：gateway 編號 + 策略短碼 + 流水號。長度不足時用短碼對照表。
- 目的：即使本地日誌全毀，回補資料仍能還原策略歸屬。
- 編不進去的資訊（母單、演算法參數、風控標記）存 WAL，以 ClOrdID 為鍵關聯。
- 流水號不落地，重啟時由 WAL 重算出下一個可用值，避免重複使用。
- 仍無法歸屬的委託與成交進 **unallocated 桶**，人工分配。

## 6. WAL

### 6.1 寫入內容
- **送出的請求**（送出前寫入）：新單、撤單、改單。含 ClOrdID、策略代號、帳號、商品、買賣別、價量、委託條件、母單等本地專屬資訊。
- **收到的回報**：原文、接收時間、來源標記（`live` / `replay` / `recovery`）。
- **對帳產生的修正**：補上的成交、判定失敗的單、人工調整。來源標記為 `recovery`。
- **檢查點**（選用）：訂單簿快照與對應的日誌位置。

### 6.2 不寫入
訂單簿、部位、風控已用額度、ClOrdID 流水號（皆可重算）。

### 6.3 格式要求
- 請求與回報寫在**同一條日誌**，共用一個本地遞增序號，確保重播順序確定。
- 每筆紀錄帶長度與檢查碼。重啟時偵測到尾端殘缺紀錄就截掉。
- 寫入方式：mmap 追加（process 崩潰時資料仍在 page cache），不必每筆 fsync。保留複寫到另一台的介面。

## 7. 狀態機規則（與順序無關）

- **成交**：以成交序號為鍵存成集合，累計成交量等於集合加總。重複自動去重。
  - 券商沒給成交序號時，用（委託書號、價、量、時間）合成鍵，並比對**出現次數**而非只判斷存在。
- **狀態**：等級為 `PendingNew < New < PartiallyFilled < 終態(Filled/Canceled/Rejected)`，只允許往前推進。終態後晚到的較低等級回報忽略。
- **數量**：累計成交取最大值；剩餘量 = 委託量 − 成交量 − 撤銷量，不直接採用回報上的值。
- **改單**：有異動序號或時間就取最新；沒有就以查詢 API 的當前值為準。
- **不變式**：成交量 + 撤銷量 ≤ 委託量。違反即告警並停止該帳號。
- **未知狀態單**：有請求、無任何回報。風控額度持續佔用；禁止直接重送，若要重送必須用同一個 ClOrdID。

## 8. 重啟流程

1. **重播 WAL**（無副作用模式：不送券商、不推策略）。從檢查點或開頭依序套用。
2. 得到崩潰當下的本地視圖：訂單簿、成交集合、部位、風控額度、下一個 ClOrdID 流水號、未知狀態單清單。
3. 進入 `Recovering` 狀態，拒收新單。
4. 連線。依策略的恢復模式決定是否先全撤（見第 10 節）。
5. 回補並建影子簿（見第 9 節）。
6. 差異比對，處理各種結果。
7. 修正寫回 WAL（來源 `recovery`），更新本地狀態。
8. 推送給策略：只補發策略還沒收過的事件（WAL 裡已有的成交視為已推送），再附上快照。
9. 對帳通過且符合恢復條件才進入 `Active`。

**快照內容**：該策略所有在途單（價格、剩餘量、累計成交、狀態）、斷線期間的成交與目前部位、後續增量流的序號切點。

## 9. 回補與對帳

### 9.1 流程（回補完再一次比，不邊回補邊比）
1. 開始回補，同時把即時回報放進緩衝區。
2. 回補資料只寫入**影子訂單簿**，不動本地狀態。
3. 收到結束標記後，把緩衝的即時回報也套進影子簿。沒有結束標記時用筆數核對或靜默逾時判定。
4. 影子簿與本地比對，產生差異清單。

### 9.2 比對粒度
- **委託層級**：當日**全部委託**（含終態）比最終狀態：狀態、價格、委託量、累計成交量、撤銷量。
- **成交層級**：以成交序號為鍵，兩邊成交集合必須完全相同。
- **其他回報**（委託確認、改單確認、狀態通知）：不逐筆比對。

### 9.3 比對結果與處理

| # | 結果 | 處理 |
|---|---|---|
| 1 | 完全一致 | 無 |
| 2 | 券商比本地新 | 正常。更新本地，補發成交事件給策略 |
| 3a | 本地有（PendingNew）、券商無 | 查詢單筆後再等一輪，仍無則判定失敗，釋放額度 |
| 3b | 本地有（已確認過）、券商無 | 異常。重新回補，仍不符則停止交易 |
| 4a | 券商有、本地無，ClOrdID 可解 | 歸回該策略，補建本地紀錄 |
| 4b | 券商有、本地無，解不出 | 進 unallocated 桶，預設撤單並告警 |
| 4c | 券商有、本地無，來自其他通路 | 標為外部單，不動它，但計入帳戶部位 |
| 5 | 本地比券商新 | 等待後重新回補。**絕不回滾本地成交**。持續不符則停止交易 |
| 6 | 同一筆單欄位衝突 | 停止該帳號交易，人工處理 |
| 7 | 回補本身失敗 | 重試；多次失敗改用查詢 API 作替代依據，維持停止交易 |

### 9.4 帳戶層級核對
逐筆比對後，再核對「本地各策略部位總和 = 券商部位查詢結果」。不符則差額進 unallocated 並告警，不自動調整任何策略部位。

### 9.5 簡化選項
因為券商每次從頭回補，訂單狀態可以完全以回補結果為準。此時本地日誌只負責：提供本地專屬資訊、找出未知狀態單、判斷哪些事件已推送給策略。初版可採此做法。

## 10. 斷線與重連

### 10.1 重連（以時間分階段，不限次數）
秒數為預設值，需可設定。

| 階段 | 行為 |
|---|---|
| 0–10 秒 | 立即重試，之後指數退避（1s、2s、4s）加隨機抖動 |
| 10–60 秒 | 主線、備援線路、備援主機輪流嘗試，發出告警 |
| 超過 60 秒 | 升級為事故。每 30 秒重試一次，持續到收盤 |

交易時段內不放棄重連。例外：
- **登入被拒**（憑證錯誤、序號過低）：立即停止重試並告警，避免帳號鎖定。
- **連線抖動**（例如 10 分鐘內斷 3 次）：連線照常重連，但停止自動恢復交易。

### 10.2 斷線期間
- 拒收新單，通知策略連線中斷。
- 在途單標為未知，不可當作已撤。風控額度繼續佔用。
- 即使交易所有斷線刪單，恢復後仍須回補確認。

### 10.3 長時間連不上
1. 透過獨立路徑撤單：備援線路上的 kill switch、券商風控介面、最後打電話給券商。
2. 斷線刪單只處理掛單，部位風險仍在，由策略或人工在其他帳號/市場對沖。
3. 恢復後當作完整重啟處理，人工確認後才開放。

### 10.4 恢復模式（每策略設定）
- `resume`：對帳後推快照，原掛單保留，續做。
- `cancel_then_resume`：先全撤，確認撤完後策略自動重新掛單。適合做市類。
- `halt`：全撤後停止，等人工放行。

判斷條件：斷線時間、對帳是否乾淨、策略與行情在斷線期間是否連續、斷線期間價格變動、市場時段。**條件衝突時取最保守的**。

```yaml
on_reconnect:
  default_action: resume
  max_outage_for_resume: 5s
  max_price_move: 0.5%
  require_clean_reconcile: true   # 不乾淨一律 halt
  max_flaps: 3 / 10min            # 超過一律 halt
  escalate_action: cancel_then_resume
```

## 11. 全撤單流程

決定全撤時**不等回補完成**，先依手上資訊送撤單。

1. 擋住新單。
2. 第一輪撤單：券商支援帳號層級批次撤單就直接用；否則用 WAL 重播出的本地活單清單逐筆撤。
3. 查詢未成交委託，對本地不知道的單（孤兒單、當時未確認的單）送第二輪撤單。
4. 回補與對帳照常進行，同時確認撤單結果。
5. 最終驗證：未成交查詢連續兩次為空才算完成。

注意事項：
- 撤單被拒是預期內的結果，只記錄，不據此更新部位。
- 撤單請求照樣先寫 WAL 再送。
- 撤單回報屬於即時回報，回補期間先放緩衝區。
- 確認前不釋放風控額度，也不通知策略「已撤」。
- 遵守流量限制，離市價近、量大的優先。

## 12. Kill Switch

### 12.1 原則
- 獨立 process、獨立設定，最好不同機器與線路。
- 無狀態：不讀 gateway 的記憶體或日誌，一切向券商查詢。
- 程式盡量簡單，可重複執行。
- 自動觸發只做撤單。平倉是獨立步驟，需人工確認。

### 12.2 流程
1. 隔離源頭：kill gateway process，或設定 gateway 送單前必查的共享旗標。
2. 查詢該帳號全部未成交單。
3. 撤單（批次或逐筆，依風險排序）。
4. 驗證：重新查詢，連續兩次為空。撤單被拒要記錄，不無限重試。
5. 回報殘留掛單與部位，發出告警。

### 12.3 連線
- 優先：專用的第二組憑證，並確認可跨 session 撤單。
- 其次：券商風控介面或帳號層級 kill switch。
- 最後：單一 session 時，先確認 gateway 已死，再接管該 session。

### 12.4 觸發與範圍
- 觸發：人工（CLI）、watchdog 偵測心跳消失、風控門檻。
- 範圍：單一策略（靠 ClOrdID 裡的策略短碼）、單一帳號、全部。

## 13. 失敗情境總表

| 情境 | 偵測 | 處理 |
|---|---|---|
| 策略崩潰，gateway 正常 | 策略心跳逾時 | 依設定撤單或保留；策略重連後推快照 |
| 網路斷線，gateway 正常 | 連線心跳逾時 | 第 10 節 |
| Gateway 崩潰，機器正常 | Watchdog | 高風險策略先觸發 kill switch；重啟走第 8 節 |
| 整機故障或磁碟損毀 | 外部監控 | 由另一台 kill switch 撤單；用複本 WAL 或純靠回補重建 |
| 送出後沒有回報 | 逾時 | 未知狀態單處理（第 7 節） |
| 券商端故障 | 回報停止、延遲暴增、大量拒單 | 停止送新單；恢復後完整對帳 |
| 對帳不一致 | Reconciler | 第 9.3 節 |
| Kill switch 失敗 | 驗證未通過 | 備援線路、電話、人工流程 |

## 14. 模擬券商與測試

Mock Broker 需支援注入：
- 斷線（任意時點，含送單後確認前）
- 回報遺失、延遲、重複
- 回補順序打亂、中間狀態合併或省略
- 回補不完整或無結束標記
- 登入被拒
- 撤單被拒（已成交、太晚）
- 外部通路下單（產生孤兒單）
- 流量限制

必測情境：
1. 送單後、收到確認前 gateway 崩潰，重啟後正確判定該單狀態。
2. 斷線期間發生成交，恢復後策略收到補發成交且不重複。
3. 回補順序與即時順序不同，最終狀態一致。
4. WAL 尾端殘缺紀錄，重啟能截掉並繼續。
5. 9.3 表中每一種比對結果。
6. 全撤期間再次崩潰，重啟後不漏撤、不誤判。
7. 連線抖動觸發 halt。
8. Kill switch 在 gateway 仍在送單時執行，最終活單為零。
9. 重啟後 ClOrdID 不重複。
10. 帳戶層級部位核對不符時進 unallocated 並停止交易。
