# Gateway Failover 情境目錄與建議處理

## 給閱讀這份文件的 agent

**背景**：我們有多個既有的（legacy）交易 gateway，各自對接不同券商或交易所，負責連線、轉送策略委託、管理回報。它們的 failover 處理程度不一。

**你的任務**：拿這份目錄逐項對照你負責的 gateway 程式碼，找出哪些情境沒處理、處理不完整或處理方式有風險，並提出改善建議。

**怎麼用這份文件**
1. 先完成第 2 節的「回補能力盤點」，因為它決定第 6 節該採哪種做法。
2. 逐項檢視第 3–9 節的情境。每個情境都有「檢查重點」，說明要在程式碼裡找什麼。
3. 依第 10 節的格式輸出分析結果。

**注意事項**
- 這份文件描述的是建議做法，不是唯一做法。各 gateway 的券商 API 能力不同，請依實際能力調整，並在報告中說明調整理由。
- 判斷「已處理」要有程式碼依據（檔案與函式），不要從命名或註解推測。找不到就標為「未處理」或「無法確認」。
- 先分析，不要直接改程式碼，除非另有指示。
- 情境編號（如 `C1`）請在報告中沿用，方便跨 gateway 比較。

## 1. 核心原則

所有情境的建議處理都由這幾條推導出來。遇到目錄沒列到的情況，用這些原則判斷。

1. **真相分兩邊**：委託狀態與成交以券商為準；策略歸屬、母單等本地專屬資訊以自己的日誌為準。
2. **先寫後送**：任何送往券商的請求，送出前先寫入本地日誌。
3. **只存事實，不存推導結果**：訂單簿、部位、風控額度由日誌重算。
4. **處理與順序無關**：回報的套用要冪等，且不依賴到達順序。
5. **不確定時假設最壞情況**：狀態未知的單視為可能還在、也可能已成交，風控額度繼續佔用。
6. **恢復期間不接新單**：對帳通過才開放交易。
7. **無法自動判定就停止交易**，交給人工，不讓程式猜測。
8. **條件衝突時取最保守的**。

## 2. 回補能力盤點（先做這一步）

不同券商的回補 API 差異很大。先回答下列問題，再決定對帳做法。

| 問題 | 影響 |
|---|---|
| 能否指定起點（序號、時間）回補，還是只能從頭？ | 從頭回補耗時隨當日筆數增加，需要「先撤單再回補」的設計 |
| 回補有沒有明確的結束標記？ | 沒有的話要用筆數核對或靜默逾時判定結束 |
| 回補順序是否保證與原始順序相同？ | 不保證的話狀態機必須與順序無關（見 C4） |
| 回補是否包含全部回報，還是只有成交或只有最終狀態？ | 決定能比對到什麼粒度 |
| 每筆成交有沒有唯一的成交序號？ | 沒有的話要用合成鍵並比對出現次數 |
| 回補期間即時回報會不會同時進來？同一條連線還是不同連線？ | 決定是否需要緩衝區 |
| 有沒有「未成交委託查詢」「單筆委託查詢」「部位查詢」？ | 用於快速撤單、未知狀態單判定、帳戶層級核對 |
| 回報會不會帶回 ClOrdID 或自訂欄位？長度限制？ | 決定策略歸屬能否從回補還原 |
| 有沒有批次撤單？撤單需要委託書號還是 ClOrdID？ | 影響全撤單流程與未確認單的處理 |
| 有沒有斷線刪單？是否可設定？ | 影響斷線期間的假設 |
| 同一組憑證能否多條 session？能否跨 session 撤單？ | 影響 kill switch 的連線方式 |
| 回補與查詢有沒有流量限制？ | 影響恢復時間與撤單排序 |

**依能力選擇對帳做法**

- **可指定序號回補（如 FIX ResendRequest）**：持久化收發序號，重連後只補缺口。重送的訊息需去重。序號被重置或跨日時這條路失效，要有退回查詢 API 的路徑。
- **只能從頭回補**：用回補資料建一份影子訂單簿，播完再和本地比對。訂單狀態可以完全以回補結果為準，本地日誌只負責本地專屬資訊、未知狀態單偵測和已推送事件的去重。
- **只有查詢 API、沒有回補**：以委託查詢和成交查詢的結果當作影子簿。中間過程拿不到，只能比對最終狀態與成交明細。
- **只回補成交**：委託狀態靠委託查詢補齊，兩者合併後再比對。

無論哪一種，都要做最後的帳戶層級部位核對（見 D9）。

## 3. A 類：程序與機器故障

### A1 策略崩潰，gateway 正常
- **風險**：策略的掛單無人管理。
- **建議**：策略與 gateway 之間有心跳。逾時後依該策略的設定撤掉其掛單，或保留等它回來。回報照常落地。策略重連後推送快照（在途單、斷線期間成交、部位、後續增量流的序號切點）。
- **檢查重點**：有沒有策略心跳；逾時後的行為是否可設定；策略重連時拿到的是完整狀態還是只有之後的增量。

### A2 Gateway 崩潰，機器正常
- **風險**：掛單仍在交易所，無人管理；期間的回報遺失。
- **建議**：watchdog 偵測並重啟。重啟流程為：重播本地日誌（不送券商、不推策略）→ 進入恢復狀態並拒收新單 → 連線 → 回補 → 對帳 → 修正寫回日誌 → 推送策略尚未收過的事件與快照 → 開放交易。
- **檢查重點**：有沒有 watchdog；重啟後狀態從哪裡來（日誌、券商，或直接歸零）；恢復期間是否擋新單；重播時會不會誤觸發送單或推送。

### A3 送單過程中崩潰
- **風險**：崩潰發生在「寫日誌後、送出前」或「送出後、確認前」，本地無法分辨該單是否存在。
- **建議**：送出前寫日誌。重啟後，有請求卻沒有任何回報的單標為未知狀態，照 C1 處理。
- **檢查重點**：寫日誌與送出的先後順序；重啟後能否列出這類單；有沒有任何路徑會自動重送。

### A4 恢復或全撤過程中再次崩潰
- **風險**：不知道哪些撤單已送出，對帳修正只做了一半。
- **建議**：撤單請求與對帳修正都寫入日誌。恢復流程設計成可重複執行，從頭再跑一次的結果相同。
- **檢查重點**：恢復流程中有沒有只存在記憶體的中間狀態；重複執行是否安全。

### A5 整機故障或磁碟損毀
- **風險**：本地日誌遺失，本地專屬資訊無法還原。
- **建議**：由另一台機器的 kill switch 先撤單。日誌複寫到另一台；沒有複本時靠券商回補和 ClOrdID 內的策略短碼重建，其餘進未分配帳。
- **檢查重點**：日誌有沒有異地複本；沒有日誌時能否啟動；能否從回補資料還原策略歸屬。

### A6 日誌尾端殘缺或損毀
- **風險**：崩潰時最後一筆只寫了一半，重啟時解析失敗或讀到錯誤資料。
- **建議**：每筆紀錄帶長度與檢查碼。重啟時偵測到尾端殘缺就截掉；中段損毀則停止並告警。
- **檢查重點**：紀錄有沒有檢查碼；重啟遇到壞資料的行為。

### A7 重啟後委託編號重複
- **風險**：ClOrdID 重複使用，券商拒單或把新單當成舊單。
- **建議**：下一個流水號由日誌重算，或編號中帶有每次啟動都會變的成分。
- **檢查重點**：流水號的來源；重啟後是否從固定值開始。

## 4. B 類：連線故障

### B1 短暫斷線
- **風險**：斷線期間的回報遺失，掛單狀態不明。
- **建議**：自動重連。立即重試後指數退避並加隨機抖動。斷線期間拒收新單、通知策略，在途單標為未知，不可當作已撤。重連後回補、對帳，通過才開放。
- **檢查重點**：有沒有自動重連與退避；斷線時是否通知策略並擋新單；重連後是否回補，還是直接繼續。

### B2 長時間無法連線
- **風險**：掛單與部位長時間無法管理。
- **建議**：以時間分階段升級，不以次數為上限。交易時段內持續重連，同時切換備援線路與主機、發出告警、透過獨立路徑撤單（kill switch、券商風控介面、電話）。恢復後當作完整重啟處理，人工確認後才開放。
- **檢查重點**：重連是否有次數上限、到上限後的行為；有沒有備援線路；有沒有告警；有沒有不依賴這條連線的撤單途徑。

### B3 登入被拒
- **風險**：重試不會成功，反覆嘗試可能造成帳號鎖定。
- **建議**：區分「連不上」與「登入被拒」。後者立即停止重試並告警。
- **檢查重點**：重連邏輯是否區分失敗原因。

### B4 連線抖動
- **風險**：反覆斷線重連，每次都自動恢復交易，掛單在不穩定的連線上進出。
- **建議**：統計一段時間內的斷線次數。超過門檻後連線照常重連，但停止自動恢復交易，等人工放行。
- **檢查重點**：有沒有抖動偵測。

### B5 連線存在但無資料
- **風險**：TCP 沒斷，但回報停止或嚴重延遲，程式以為一切正常。
- **建議**：應用層心跳逾時偵測。送單後回報延遲超過門檻也視為異常，停止送新單。
- **檢查重點**：有沒有應用層心跳；有沒有回報延遲監控。

### B6 恢復後續做或全撤的決策
- **風險**：過時的掛單在恢復後繼續留在市場，或不必要地撤掉長期掛單。
- **建議**：每個策略設定恢復模式：`resume`（保留掛單續做）、`cancel_then_resume`（先全撤再讓策略重掛）、`halt`（全撤後等人工）。判斷條件包含斷線時間、對帳是否乾淨、策略與行情在斷線期間是否連續、期間價格變動、市場時段。任何一項指向 halt 就 halt。
- **檢查重點**：恢復後的行為是寫死的還是可設定的；是否考慮斷線時間長短。

## 5. C 類：單筆委託的不確定狀態

### C1 送出後沒有回報
- **風險**：可能沒送出、回報遺失，或對方還在處理。誤判為失敗會漏算部位，誤判後重送會變成兩筆委託。
- **建議**：確認前視為可能成交，風控額度先佔用。用單筆查詢確認；查不到則等一段時間再查，連續查不到才判定失敗。禁止直接重送；必須重送時使用同一個 ClOrdID。
- **檢查重點**：有沒有送單逾時處理；逾時後是否自動重送；逾時後額度是否被釋放。

### C2 撤單或改單送出後沒有回報
- **風險**：不知道原單是否還在、是哪個價量。
- **建議**：原單維持「撤單中」狀態，不釋放額度。用查詢確認。
- **檢查重點**：撤單逾時後原單被標成什麼狀態。

### C3 撤單被拒
- **風險**：把拒絕當成錯誤而中斷流程，或據此直接更新部位。
- **建議**：撤單被拒（已成交、已撤、太晚）是預期內的結果。只記錄，實際狀態等成交回報或對帳確認。
- **檢查重點**：撤單被拒後的狀態轉換；全撤流程遇到拒絕是否會卡住。

### C4 回報順序錯亂或晚到
- **風險**：用「最後收到的回報」覆蓋狀態，已終結的單被改回活單，或成交量倒退。
- **建議**：狀態只能往前推進（待確認 < 已委託 < 部分成交 < 終態）。成交以成交序號為鍵存成集合，累計成交量由集合加總。剩餘量由委託量、成交量、撤銷量推導。
- **檢查重點**：狀態更新是否直接採用回報上的值；有沒有狀態倒退的防護。

### C5 重複回報
- **風險**：同一筆成交被計算兩次，部位錯誤。
- **建議**：以成交序號去重。券商沒給成交序號時，用（委託書號、價、量、時間）合成鍵，並比對出現次數，因為同鍵可能有多筆真實成交。
- **檢查重點**：成交有沒有去重；去重的鍵是什麼。

## 6. D 類：回補與對帳

做法依第 2 節盤點結果調整。以下以「只能從頭回補」為基準描述。

### D1 回補流程本身
- **建議**：回補資料寫入影子訂單簿，不直接動本地狀態。播完再一次比對，不要邊回補邊比，因為回補的中間狀態落後於本地，會產生假差異。
- **比對粒度**：當日全部委託（含已終結的）比最終狀態；成交以成交序號逐筆比對；委託確認等中間回報不逐筆比對。
- **檢查重點**：回補資料是直接套進正式狀態，還是先隔離；比對範圍是否包含已終結的單。

### D2 回補期間即時回報同時進來
- **風險**：即時回報與回補資料交錯，狀態被舊資料覆蓋或事件重複。
- **建議**：回補期間即時回報先放緩衝區，回補結束後再套用。狀態機與順序無關的話，交錯也不會出錯。
- **檢查重點**：回補期間即時回報的去向。

### D3 回補沒有結束標記或中途失敗
- **建議**：用筆數核對或靜默逾時判定結束。失敗則重試；多次失敗改用查詢 API 作替代依據，並維持停止交易。
- **檢查重點**：如何判定回補完成；回補失敗時是否仍開放交易。

### D4 券商比本地新
- **說明**：斷線期間漏了回報，屬於正常情況。
- **建議**：更新本地，補發成交事件給策略。只補發策略沒收過的（本地日誌已有的視為已推送）。
- **檢查重點**：補發時會不會把已推送過的成交再推一次。

### D5 本地有、券商沒有
- **建議**：本地是待確認的單，照 C1 處理後判定失敗並釋放額度。本地已收過委託確認的單卻不在回補裡，代表回補不完整或查錯帳號，重新回補，仍不符則停止交易。
- **檢查重點**：這兩種情況是否被區分。

### D6 券商有、本地沒有（孤兒單）
- **建議**：ClOrdID 能解出策略就歸回該策略；解不出就進未分配帳，預設撤單並告警；來自其他通路（人工下單）的標為外部單，不動它但計入帳戶部位。
- **檢查重點**：遇到不認得的委託或成交時是丟棄、報錯，還是有處理。

### D7 本地比券商新
- **說明**：本地有成交，回補裡沒有。通常是回補還沒播完或券商資料延遲。
- **建議**：等待後重新回補。絕不回滾本地已記錄的成交。持續不符就停止交易，人工處理。
- **檢查重點**：對帳時是否會無條件以券商資料覆蓋本地。

### D8 同一筆單欄位衝突
- **說明**：價、量、買賣別不同，代表編號撞號或程式錯誤。
- **建議**：停止該帳號交易，人工處理。

### D9 帳戶層級部位不符
- **建議**：逐筆比對後，核對「本地各策略部位總和 = 券商部位查詢結果」。不符時差額進未分配帳並告警，不自動調整任何策略的部位。也建議在盤中定時執行。
- **檢查重點**：有沒有帳戶層級的核對。

### D10 對帳修正沒有持久化
- **風險**：修正只改了記憶體，下次重啟算出不同結果。
- **建議**：對帳產生的修正當作事實寫入日誌，並標記來源。
- **檢查重點**：對帳結果是否落地。

## 7. E 類：策略歸屬與本地專屬資訊

### E1 策略代號不會傳到券商
- **風險**：同帳號多策略共用時，回補回來的委託與成交無法歸屬。
- **建議**：分層處理。
  1. 把 gateway 編號、策略短碼、流水號編進 ClOrdID 或券商自訂欄位，讓回補資料自帶歸屬。
  2. 編不進去的資訊（母單、演算法參數、風控標記）存本地日誌，以 ClOrdID 為鍵關聯。
  3. 策略重連時上報自己認為的在途單，由 gateway 比對認領。
  4. 仍無法歸屬的進未分配帳，人工分配。
- **檢查重點**：策略與委託的對應存在哪裡；只存記憶體的話，重啟後如何還原。

## 8. F 類：券商與交易所端

### F1 券商或交易所故障
- **徵兆**：連線正常但回報停止、延遲暴增、大量拒單。
- **建議**：停止送新單。對方恢復後可能重置序號或重送舊回報，處理要冪等，並做一次完整對帳。對方宣告某段時間委託無效時，以官方公告為準人工修正。
- **檢查重點**：有沒有異常拒單率或延遲的偵測；有沒有人工修正狀態的途徑。

### F2 誤信斷線刪單
- **風險**：假設斷線後掛單都被刪了，實際上沒有或只刪了一部分。
- **建議**：斷線刪單只是額外保護，恢復後仍須回補確認。它只處理掛單，部位風險仍在。
- **檢查重點**：程式是否在斷線時直接把掛單標成已撤。

### F3 市場時段限制
- **說明**：集合競價等時段撤單或改單可能被拒。
- **建議**：辨識這類拒絕原因，時段結束後重試。恢復模式的判斷納入市場時段。

### F4 流量限制
- **風險**：恢復時大量撤單或查詢撞到上限，關鍵請求被擋。
- **建議**：撤單按風險排序，離市價近、量大的優先。回補與查詢避免佔用撤單的額度。
- **檢查重點**：有沒有送出速率控制；撞到限制後的行為。

## 9. G 類：緊急撤單

### G1 恢復時決定全撤
- **建議**：不等回補完成，先依手上資訊送撤單。
  1. 擋住新單。
  2. 有帳號層級批次撤單就直接用；否則用本地日誌重播出的活單清單逐筆撤。
  3. 查詢未成交委託，對本地不知道的單送第二輪撤單。
  4. 回補與對帳照常進行。
  5. 未成交查詢連續兩次為空才算完成。
- **注意**：撤單請求先寫日誌；確認前不釋放額度、不通知策略已撤；撤單回報在回補期間照樣進緩衝區。
- **檢查重點**：全撤是否依賴完整對帳；孤兒單與未確認的單會不會漏撤；如何確認真的撤完。

### G2 獨立 kill switch
- **建議**：獨立 process，最好不同機器與線路。無狀態，不讀 gateway 的記憶體或日誌，一切向券商查詢。流程為隔離源頭（停掉 gateway 或設共享旗標）→ 查詢 → 撤單 → 驗證 → 回報殘留掛單與部位。自動觸發只做撤單，平倉需人工確認。
- **連線**：優先用專用的第二組憑證；其次是券商風控介面；只有單一 session 時，需先確認 gateway 已死再接管。
- **觸發**：人工、watchdog、風控門檻。範圍可選單一策略、單一帳號或全部。
- **檢查重點**：gateway 掛掉時有沒有任何程式能撤單；該程式是否依賴 gateway 的狀態；有沒有定期演練。

### G3 Kill switch 失敗
- **建議**：備援線路、券商交易室電話、書面應變程序。部分撤單失敗時輸出殘留清單交給人工。

## 10. 分析結果的輸出格式

請依下列格式回報。

**一、回補能力盤點**
第 2 節表格逐題作答，並說明據此選擇的對帳做法。

**二、情境對照表**

| 編號 | 現況 | 依據（檔案與函式） | 差距說明 | 建議做法 | 優先度 |
|---|---|---|---|---|---|
| A1 | 已處理 / 部分處理 / 未處理 / 不適用 / 無法確認 | | | | P0–P2 |

**三、目錄未涵蓋的情境**
分析時發現這份目錄沒列到、但該 gateway 會遇到的情境。請一併列出，並用第 1 節的原則提出處理方式。

**四、需要人回答的問題**
例如券商 API 行為無法從程式碼確認的部分。

**優先度判定**
- **P0**：可能造成重複下單、漏算或重複計算成交、部位錯誤、活單無人管理且無法撤掉。
- **P1**：恢復後需要人工介入才能正確運作，或恢復時間過長。
- **P2**：可觀測性、可設定性、演練等改善。
